# Commerce: a Shopify-style backend built with the platform

A multi-store commerce backend described as data, generated by the Backend Builder, and filled with realistic
data. It exists to be built on (your frontend) and to show where the platform stops: see `LIMITATIONS.md`.

| File | What it is |
|---|---|
| `blueprint.py` | The model: 32 entities, 32 relations, roles, sign-up fields and the permission matrix |
| `build_commerce.py` | Creates the project in a running builder through its public API, validates it, saves the result |
| `spec.json` | The exported spec of the project (the contract the generator renders) |
| `backend/` | The generated project, ready to run (219 files; its own tests, migrations, Docker setup) |
| `populate_commerce.py` | Fills the running backend: stores, staff, customers, catalog, orders in every state |
| `probe_limits.py` | Tries to break it; writes `probe_results.json` |
| `USERS.md`, `seeded.json` | The seeded accounts (every password is `Demo-pass-2026!`) and ids |

## Model in one paragraph

Each **store is a tenant**: signing up creates a store and makes you its `admin`. Staff arrive by invitation with a
role (`manager`, `catalog`, `fulfillment`, `support`, `marketing`; `admin` inherits `manager`); `customer` is the default
role. Every entity is tenant-scoped. Money is `decimal`; orders keep snapshots of what was bought (title, SKU, price) and
are never deleted. Sign-up fields: display name, language, marketing opt-in, job title. Auth is the built-in one (RS256
tokens, Redis refresh tokens, email verification).

## Run it

You need Docker and a running builder (`docker compose up -d` in the repo root).

```bash
# 1. a mail catcher: invitations and verification emails land here (http://localhost:8025)
docker run -d --name mailpit -p 1025:1025 -p 8025:8025 axllent/mailpit

# 2. build the project in the builder (add --reset to recreate it), save spec.json and backend/
python examples/commerce/build_commerce.py

# 3. start the generated backend on http://localhost:18100
cd examples/commerce/backend
python -m app.auth.keys            # prints AUTH_JWT_PRIVATE_KEY=... : put it in .env with the next lines
printf 'API_PORT=18100\nSMTP_USERNAME=\nSMTP_PASSWORD=\n' >> .env
docker compose -p commerce up -d --build
cd ../../..

# 4. fill it with data, then (optionally) attack it
python examples/commerce/populate_commerce.py
python examples/commerce/probe_limits.py
```

`python -m app.auth.keys` needs the `cryptography` package (the builder's environment has it:
`uv run python -m app.auth.keys` from `backend/`). Interactive docs: http://localhost:18100/docs. To start over:
`docker compose -p commerce down -v` in `backend/`, then steps 3 and 4.

## Using it from a frontend

- Sign in with `POST /auth/login {email, password}`; send `Authorization: Bearer <access_token>`. Refresh with
  `POST /auth/refresh`. Try `ava@acme.test` (store owner), `carl.catalog@acme.test` (catalog), `sam.support@acme.test`
  (support), `zara@acme-shopper.test` (customer).
- Every list is `GET /<plural>?limit=&offset=&sort=&q=` plus exact-match filters on the fields named in the entity's
  section of `backend/README.md`; responses are `{items, total, limit, offset}`.
- Parents return child **ids**, not rows (`order.lines`, `product.variants`): load children with a second request or
  filter the child list. Money comes back as strings with 6 decimals.
- The backend has no checkout: your application creates the order, its lines, the transaction and the stock update
  (see `place_order` in `populate_commerce.py` for the sequence and the arithmetic).
- The seeded data includes edge cases on purpose: draft/archived/soft-deleted products, out-of-stock and "continue
  selling" variants, a 10,000-character description, Unicode names, expired/future/exhausted discounts, a disabled gift
  card, disabled and invited customers, abandoned carts, pending/rejected reviews, and orders that are paid,
  pending, partially fulfilled, fully or partly refunded, voided, cancelled for fraud and international.

Read `LIMITATIONS.md` before designing screens: several things a storefront normally takes for granted (anonymous
browsing, customers seeing only their own orders, per-store unique SKUs) are not available yet.
