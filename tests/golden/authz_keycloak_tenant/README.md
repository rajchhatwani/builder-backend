# Crm

Keycloak organizations as tenants, plus custom sign-up fields

Generated by Backend Builder: FastAPI + SQLAlchemy 2 (async) + Alembic + PostgreSQL.
This code is **yours now**. It is generated once; there is no regeneration or merge step, so
edit it freely.

## Run

```bash
docker compose up --build
```

The API starts on <http://localhost:8000> (set `API_PORT` to change it) after applying the
Alembic migration. Interactive docs: <http://localhost:8000/docs>. Health: `GET /health`,
readiness (checks the database): `GET /ready`.

To run without Docker: start a Postgres, copy `.env.example` to `.env`, then

```bash
pip install -r requirements.txt -r requirements-dev.txt
alembic upgrade head
uvicorn app.main:app --reload
```

## Authentication (Keycloak)

Sign-in, sign-up, password reset, MFA and social login are handled by **Keycloak**, not by this
API. The API only **verifies Keycloak access tokens** and applies your roles and permissions.
Send `Authorization: Bearer <access_token>` to protected routes.

| Route | What it does |
|---|---|
| `GET /auth/me` | The signed-in user's profile (created the first time they call the API) |
| `DELETE /auth/me` | Erase what this API stores about the user (email, name, roles). Their rows keep an id that no longer leads to a person. Delete the Keycloak account in Keycloak too, until then they cannot sign in here again |

Protect your own routes with `CurrentUser` and `require_roles("...")` from `app/auth/deps.py`.
Access to the CRUD endpoints follows the permissions in your spec (`app/routers/*.py`).

### What the API checks on every token

Signature (RS256 only, keys fetched from Keycloak, never from the token), issuer, audience
(`crm-api`), token type, expiry and not-before. Anything else is a plain `401`.
Roles come from the token's `resource_access.crm-api.roles` and are re-read on every
request, so a role removed in Keycloak stops working when the user's access token expires
(15 minutes). Disable a user at once by setting `is_active=false` on their `auth_users` row.

### Tenants

Every **Keycloak organization is a tenant**. Create organizations in the Keycloak admin console
(*Organizations*) and add your users to them. A user must belong to exactly one organization: the API
refuses (`403 no_organization`) a token that carries none, and Keycloak leaves the organization out of the
token of someone in several until the app asks for one with the scope `organization:<alias>`. Tenant ids are
derived from the organization's alias, so they are the same in every environment. `GET /auth/tenant` returns
the current one. Rows of entities with the `tenant` row rule are only ever visible inside their tenant.

### Extra sign-up fields

`company`, `age`, `plan`, `newsletter`, `site`, `born`, `score`, `mobile`, `notes` are Keycloak user attributes: the
sign-up page asks for them, Keycloak validates them and keeps them, and they reach the API as claims of the same
name, copied to `auth_users` and returned by `GET /auth/me`. A value the API cannot use (wrong type, too long) is
stored as empty rather than breaking a request. A field missing from a token leaves the stored value as it is.

### First run

1. `cp .env.example .env` and fill in `KEYCLOAK_DB_PASSWORD`, `KC_BOOTSTRAP_ADMIN_PASSWORD`.
2. `docker compose up --build`. Keycloak takes about a minute to start, then the API follows.
3. Open <http://localhost:8081/admin> (the address in `KEYCLOAK_PUBLIC_URL`) and sign in as the bootstrap admin.
   **Create your own admin account in the `master` realm, then delete the bootstrap one.**
4. Switch to the **crm** realm. Create users under *Users* and give them roles on the `crm-api` client (*Users, Role mapping*).
5. Get a token: open <http://localhost:8000/docs>, press **Authorize** and sign in. Or build your own login page with the **crm-web** client (authorization code flow with PKCE; the callback URLs are the ones you gave when designing the project).

The realm in `keycloak/realm.json` is imported **once**, the first time Keycloak starts on an empty
database. Later changes are made in Keycloak's admin console. To apply this project's clients and
roles again after changing `keycloak/clients.json`, run `python scripts/keycloak_register.py` (see the
script's header). To start over from the file, run `docker compose down -v`.

### Before going to production

- Put a reverse proxy with **TLS** in front of Keycloak, set `KEYCLOAK_PUBLIC_URL` to its https address,
  `KC_PROXY_HEADERS: xforwarded` under the `keycloak` service in `docker-compose.yml` (only behind a proxy you control) and `APP_ENV=production`; the API then
  refuses a non-https issuer. Block `/admin` from the internet at the proxy and reach it over a VPN.
- Redirect URLs in the realm are exact; update them in the `crm-web` client when your
  frontend's address changes. Set `API_PUBLIC_URL` to the API's real address (it is used by Swagger UI sign-in).
- Replace the `postgres` passwords and the bootstrap admin, back up the `keycloak_db_data` volume,
  and decide where Keycloak's logs go: they contain the audit trail (sign-ins, failures and admin changes;
  kept 90 days in Keycloak as well).
- CORS is open (`CORS_ORIGINS=["*"]`) by default; set it to your frontend's origin. Swagger UI (`/docs`) is on
  by default; remove it in production by creating the app with `docs_url=None, openapi_url=None` in `app/main.py`.
- The API does not hold any Keycloak secret. Keep it that way: browsers must use the public client, never a secret.

### Switching identity provider

The first start records which provider this database belongs to (`auth_provider_lock`). A build for a
different provider or realm refuses to start on it, because users would not carry over. To switch on
purpose, start once with `AUTH_ALLOW_PROVIDER_SWITCH=true`.

## Database migrations

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

## Extending

- `app/custom_routers/`: add a module defining `router = APIRouter(...)`; it is mounted
  automatically.
- `app/hooks/`: place your own business logic here and call it from your routers.
- `app/crud/<entity>.py`: per-entity repositories; subclass or edit to add queries.

Names in generated code use a leading underscore (`_orm`, `_sa`, ...) for library aliases so
that your field names can never shadow them.

## Not included

Authorization rules on the entity endpoints, background jobs, caching and webhooks.
Soft-deleted rows are hidden from the API but still count for unique constraints and their
relation `on_delete` rules are not applied.
