# Tenant Guard

Multi-tenant HR with guarded fields across transitions, documents, history, search, realtime and metrics

Generated by Backend Builder: FastAPI + SQLAlchemy 2 (async) + Alembic + PostgreSQL.
This code is **yours now**. It is generated once; there is no regeneration or merge step, so
edit it freely.

## Run

```bash
docker compose up --build
```

The API starts on <http://localhost:8000> (set `API_PORT` to change it) after applying the
Alembic migration. Interactive docs: <http://localhost:8000/docs>. Health: `GET /health`,
readiness (checks the database): `GET /ready`.

To run without Docker: start a Postgres, copy `.env.example` to `.env`, then

```bash
pip install -r requirements.txt -r requirements-dev.txt
alembic upgrade head
uvicorn app.main:app --reload
```

## Search

- `GET /employees/search?q=&limit=` searches `name`, `notes` of Employee.

A search sees exactly the rows the caller may list (roles, tenant, owner / row scope, policy; soft-deleted rows never),
`total` counts only those rows, and a field the caller may not read is neither searched nor returned. `q` is 1-200
characters and `limit` at most 100 (default 20). Engine, set with environment variables:

| Variable | Meaning |
|---|---|
| `SEARCH_BACKEND` | `fts` (default: Postgres full-text, nothing to run) or `opensearch`. `opensearch-fake` is an in-memory engine for tests and is refused in production. |
| `SEARCH_OPENSEARCH_URL` | Required with `opensearch`: the app refuses to start without it (no silent fallback). |
| `SEARCH_OPENSEARCH_API_KEY` | Optional credential sent as `Authorization: ApiKey ...`; never logged. |
| `SEARCH_OPENSEARCH_INDEX_PREFIX` | Index name prefix (default `app-`). |

With `opensearch`, the index only ranks candidate ids; rows are always re-read from Postgres through the access scope, so an
out-of-date index cannot show a row the caller may not see. Writes through the API keep the index in step after commit; rows
created some other way (imports, SQL) are not indexed until they are saved again, or until you rebuild the index:
`python -m app.search.reindex [--entity NAME]` streams every live row of the searchable entities (in batches of 500) into the
configured engine, through the same document builder as the write hook (with `fts` it only says there is no index). Run it
after switching from `fts` to `opensearch`. When the engine is down the search answers 503.

## Realtime

`GET /realtime/stream` is a Server-Sent Events stream of what changes in: Employee.
Each event is `{"id", "topic", "type", "data": {"entity", "record_id", "op"}, "at"}` with `op` = `created`, `updated` or
`deleted` (a state-machine transition is an `updated`): it names the record and never carries a field value, so read the record through the API (which applies your
field rules). Send the access token as for any other route.

- Resume with the `Last-Event-ID` header (browsers do it by themselves) or `?last_event_id=`: events after that id are
  replayed in order, exactly once, then the stream follows live. Without a cursor only new events arrive.
- A cursor that cannot be replayed (older than the retention, or from another database) gets one `resync` event with the
  new cursor: reload what you show.
- You receive only events of entities you may `list`; for owner / role-scoped and tenant-scoped entities only events of
  rows inside your own scope. Entities governed by abac / pbac policies are not streamed.
- A heartbeat comment every 15 s keeps the connection open; the stream ends after 300 s and the client reconnects (it is
  authorised again each time). At most 5 live streams per person and 20 connects per minute (429 beyond that, in-process
  counters: with several workers the limits apply per worker).
- The event log is the table `rt_events`, written in the same transaction as the change, so a rolled-back write leaves no
  event. Events older than 24 h or beyond the newest 10 000 are pruned (every 100th write does it; `python -m app.realtime.prune`
  does it on demand). Writes that do not go through the repositories (raw SQL, imports) are not announced. Tracked writes
  take one short database lock each, so they are serialised with each other.

| Variable | Meaning |
|---|---|
| `REALTIME_MAX_STREAMS_PER_USER` | Concurrent streams per person (default 5). |
| `REALTIME_MAX_STREAMS` | Concurrent streams in this process, all people together (default 50); more get 503 `realtime_at_capacity`. |
| `REALTIME_RECONNECT_MAX` | Connects per person per minute (default 20). |
| `REALTIME_MAX_STREAM_SECONDS` | Stream age before the client must reconnect (default 300). |
| `REALTIME_POLL_SECONDS` | How often the stream looks for new events (default 0.5); an idle stream backs off up to `REALTIME_IDLE_POLL_SECONDS` (default 1). |

## Metrics

`GET /metrics` lists the metrics you may read and `GET /metrics/{key}` computes one in the database:
- `employee_by_status`: By status (count on Employee, grouped by status).
- `employee_count`: Employees (count on Employee).
- `salary_total`: Salary total (sum of salary on Employee).

A metric is computed over exactly the rows you may list (soft-deleted, owner / tenant scope applied), so two people can
get different numbers from the same definition. You need the `list` permission on the entity (else 403), and a metric
that uses a field you may not read (the field, the group-by or a filter) is refused with 403. Sums, minimums and maximums
are exact; `avg` is rounded to 6 decimal places (half to even); results other than counts are decimal strings without
trailing zeros; counts are integers; an empty set gives 0 for count / sum and `null` for avg / min / max. With a group-by
the answer has `groups` sorted by key, the empty key last, and `value` is the total over all groups.

## Authentication

Accounts, JWT sign-in and the email / mobile flows live in `app/auth/` (routes under `/auth`).
Set the secrets from `.env.example` in `.env` before starting: `AUTH_JWT_SECRET` is required and
`docker compose up` refuses to start without it. Secrets are read from the environment only.

| Route | What it does |
|---|---|
| `POST /auth/register` | Create an account (email, password, optional `phone` in E.164) |
| `POST /auth/login` | Email + password -> access and refresh token |
| `POST /auth/refresh` | Rotate the refresh token (a reused token revokes its whole chain) |
| `POST /auth/logout` | Revoke a refresh token chain |
| `GET /auth/me` | The signed-in account |
| `DELETE /auth/me` | Disable the account (soft delete) |
| `POST /auth/change-password` | Change password and sign out everywhere |
| `POST /auth/email/verify`, `POST /auth/email/resend-verification` | Confirm an email address (required before sign-in) |
| `POST /auth/magic-link/request`, `POST /auth/magic-link/consume` | Passwordless sign-in by emailed link |
| `POST/GET /auth/invitations`, `DELETE /auth/invitations/{id}` | Admins email one-time registration links |
| `POST /auth/password-reset/request`, `POST /auth/password-reset/confirm` | Reset a password by emailed link |

Send `Authorization: Bearer <access_token>` to authenticated routes. Protect your own routes with
`CurrentUser` and `require_roles("...")` from `app/auth/deps.py`.

Emailed links point at `https://tenantguard.example.com` (`/verify-email`, `/magic-link`, `/reset-password`, each with `?token=`);
your frontend should read the token and call the matching API route.

Limits per client address: failed sign-ins 5/15minutes (successful ones are not counted), registration 10/hour, email / SMS requests 3/hour.
They are counted in process memory, so they are per worker.

Access to the CRUD endpoints follows the permissions in your spec (`app/routers/*.py`, see `_ACCESS`
at the top of each router): the roles that may call an operation and, for some, a row rule
(`owner`, `role_scoped` or `custom_filter`). Operations without a permission are public. Rows
outside a caller's scope are reported as 404. `tests/test_access.py` checks the rules.

## Database migrations

`alembic/versions/0001_initial.py` and `0002_auth.py` were rendered from your model. For later changes edit
the SQLAlchemy models in `app/models/` and run:

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

### Upgrading a deployed project

Optional features ship their own migration under a fixed revision id, and the revisions are chained in
id order each time the project is generated. If you enable a feature whose revision id is LOWER than a
revision your database has already applied, `alembic upgrade head` will NOT apply it: Alembic sees the
database at a later revision and treats the earlier one as done. For a deployed database use the
builder's migration plan or apply that feature's migration by hand (for example with
`alembic upgrade <revision>` on a copy first, or by running its SQL), then check `alembic current`.
Enabling a feature with a higher id than your database's head is safe.

## Extending

- `app/custom_routers/`: add a module defining `router = APIRouter(...)`; it is mounted
  automatically.
- `app/hooks/`: place your own business logic here and call it from your routers.
- `app/crud/<entity>.py`: per-entity repositories; subclass or edit to add queries.

Names in generated code use a leading underscore (`_orm`, `_sa`, ...) for library aliases so
that your field names can never shadow them.

## Not included

Authorization rules on the entity endpoints, background jobs, caching and webhooks.
Soft-deleted rows are hidden from the API but still count for unique constraints and their
relation `on_delete` rules are not applied.
