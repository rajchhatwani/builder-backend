# Invoice Jobs

Invoices with background jobs: a weekly dunning run and a retrying delivery job

Generated by Backend Builder: FastAPI + SQLAlchemy 2 (async) + Alembic + PostgreSQL.
This code is **yours now**. It is generated once; there is no regeneration or merge step, so
edit it freely.

## Run

```bash
docker compose up --build
```

The API starts on <http://localhost:8000> (set `API_PORT` to change it) after applying the
Alembic migration. Interactive docs: <http://localhost:8000/docs>. Health: `GET /health`,
readiness (checks the database): `GET /ready`.

To run without Docker: start a Postgres, copy `.env.example` to `.env`, then

```bash
pip install -r requirements.txt -r requirements-dev.txt
alembic upgrade head
uvicorn app.main:app --reload
```

## Endpoints

### Invoice: `/invoices`

| Operation | Route |
|---|---|
| list | `GET /invoices?limit=&offset=&sort=` (default page 20, max 100) |
| get | `GET /invoices/{id}` |
| head | `HEAD /invoices/{id}` |
| create | `POST /invoices` |
| replace | `PUT /invoices/{id}` |
| update | `PATCH /invoices/{id}` |
| delete | `DELETE /invoices/{id}` |

Sort by: `created_at` (prefix `-` for descending).

Errors always look like `{"code": "...", "message": "...", "details": []}`.

## Database migrations

`alembic/versions/0001_initial.py` was rendered from your model. For later changes edit
the SQLAlchemy models in `app/models/` and run:

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

### Upgrading a deployed project

Optional features ship their own migration under a fixed revision id, and the revisions are chained in
id order each time the project is generated. If you enable a feature whose revision id is LOWER than a
revision your database has already applied, `alembic upgrade head` will NOT apply it: Alembic sees the
database at a later revision and treats the earlier one as done. For a deployed database use the
builder's migration plan or apply that feature's migration by hand (for example with
`alembic upgrade <revision>` on a copy first, or by running its SQL), then check `alembic current`.
Enabling a feature with a higher id than your database's head is safe.

## Tests

```bash
make test
```

runs the smoke tests inside Docker against a separate `app_test` database (created on
demand, never your dev database).

## Extending

- `app/custom_routers/`: add a module defining `router = APIRouter(...)`; it is mounted
  automatically.
- `app/hooks/`: place your own business logic here and call it from your routers.
- `app/crud/<entity>.py`: per-entity repositories; subclass or edit to add queries.

Names in generated code use a leading underscore (`_orm`, `_sa`, ...) for library aliases so
that your field names can never shadow them.

## Not included

Authentication and authorization, background jobs, caching, webhooks and rate limiting.
Soft-deleted rows are hidden from the API but still count for unique constraints and their
relation `on_delete` rules are not applied.
